## 20261108-v1 — v2.0.0（首发，替代早期原型）

### 变更说明

1. **插件定名 `mame_kbd`**，源码目录 / 部署目录 / `plugin.json` / `ini\plugin.ini` 条目四处一致。
2. **屏幕下方一行四列显示 P1~P4**：每列一个玩家，标题行显示 `P1`~`P4`。
3. **方向键一行 4 格**，按 上/下/左/右 固定顺序；格宽不足时自动省略中文前缀只显示绑定名（4 格顺序固定，信息不丢）。
4. **第 2 行固定两格「选择」「开始」**；没有对应输入时显示 `选择:--` / `开始:--` 保持版式一致。
5. **只显示游戏真实分配了的按键**，按键行按数量自适应：2~4 个 → 每行 1 格；5~6 个 → 每行 2 格；7 个以上 → 每行 3 格（可在菜单强制改成 1/2/3）。
6. **按下即变色高亮**：按下项前景改亮绿 `0xFF00FF66` + 暗绿半透明底 `0xB0008020`，同一行其他格不受影响。
7. **配置按 ROM 名独立保存**：`settings_<rom>.ini`，先用 `settings_default.ini` 打底再用本 ROM 覆盖，避免不同 ROM 互相污染。
8. **中文标签**，可在菜单切换为 `U/D/L/R`、`Sel/Sta`。
9. **绑定名精简**：去掉 `Kbd ` 前缀，手柄显示为 `J1`/`J2`，避免窄格被截断成 `..`。
10. **菜单**（MAME 内 Tab → 插件菜单 → `KBD 按键对照表`）可实时调整：显示开关、列布局、标签语言、每行按键数、选择/开始行、按下高亮、绑定显示（首个/全部）、行距、底部边距、列间隙、背景不透明度、字符宽度估计，并含诊断信息段。

### 关键技术决策（后续维护必读）

| 问题 | 决定 | 理由 |
|---|---|---|
| 如何识别玩家/语义 | 用 `ioport:input_type_to_token(ty, pl)` 拿 token 再正则解析，**不硬编码 IPT_ 枚举数值** | MAME 改枚举值不受影响；比硬编码 47/48/49/50、60~75 稳 |
| 方向键 token | 必须先匹配 `^P%d+_JOYSTICK_(%u+)$` | 街机方向键真实 token 是 `P1_JOYSTICK_UP`，不是 `P1_UP` |
| 玩家号来源 | **一律取自 token 尾部数字**，不信 `field.player` | `START1`/`START2`/`COIN1` 的 `field.player` 恒为 0 |
| 是否按 type_class 过滤 | **不按 type_class 黑名单过滤**，靠 token 白名单天然过滤 | `START1`/`COIN1`/`SERVICE1` 的 type_class 都是 `misc`，套黑名单「开始」永远不显示 |
| 按下判定 | 首选 `ioport:type_pressed(ty, player)`，回退 `port:read()` 按位与非零 | 实测 `field.defvalue` 恒为 0，拿它当未按电平会漏判；回退路径下 `==0` 会全量误判 |
| Lua 版本兼容 | 全文件不用位运算符，用算术 `band()` 模拟 | MAME 内置 Lua 版本无法确认，写成 5.1 兼容最安全 |
| 绑定文本 | `input:seq_name()` 会输出整串 `A or B or C`，改用 `seq_to_tokens` 取第一个再 `code_name` | 整串在窄格子里完全没法看 |

## 20261108-v2 — v2.1.0

### 变更说明

1. **修 P4 横向溢出**：`Num 8`/`Num 2`/`Num 4`/`Num 6` 原本一直画到画面右缘之外。根因是 `char_px`（UI 字体半角字符宽度估计）取值偏小，`fit()` 算出的可用宽度过大而没触发截断。
2. **`char_px` 默认值按实测标定**：从 8 → 13 → 18 → 最终 **15**。实测依据（1351px 窗口、一行四列）：`Down`=65px/4 字、`1:Right Ctrl`=235px/12 字，平均约 16px；每格仅约 82px。取 15 略保守，配合第 3 条缩写后 5 字可过、6 字截断。上下限同步放宽到 4..32（原 4..24 会把新默认值夹掉）。
3. **新增多词按键名缩写 `shrink_words()` + `ABBR` 表**：一行四列时每格只有约 82px，「Num 8」这 5 个字正好卡满、四格连排会糊成一片，「Num Enter」9 字必然截断。现在压成 `N8`/`NEnt`/`N0`/`NumDel`，长单词按表缩写（`Control`→`Ctrl`、`PageDown`→`PgDn`、`Backspace`→`Bksp` 等）。
4. **单字词不缩写**：`Down`/`Right`/`Left` 这类 4~5 字在 82px 下放得下，缩成 `Dn`/`Rt` 反而更难认，所以 `#words <= 1` 直接原样返回。
5. **选择/开始行改「标签优先」三级压缩**：① `开始:J1 Sta` 原样 → ② 去掉绑定名里的空格 `开始:J1Sta`（保住标签且键名完整）→ ③ 实在放不下才只显示绑定名。此前直接按剩余宽度截断会得到 `开始:J1 ..`，键名反而看不懂。
6. **修 `fit()` 函数首行与函数声明挤在同一行**（`local function fit(text, maxw)	if not text...`），属之前批量替换留下的行合并，不影响语义但已规整。
7. 版本号 2.0.0 → **2.1.0**（`init.lua` 的 `exports.version` 与 `plugin.json` 两处同步）。

## 20261108-v3 — v2.3.0

### 变更说明

1. **修「P2~P4 的开始按下不变色」**：根因是 `field_pressed()` 把「从 token 尾部解析出的玩家号」传给了 `ioport:type_pressed(ty, player)`。`IPT_START1..4`（ty=7..10）本身已内含玩家号、其字段 `player` 恒为 0，拿 1 去查 ty=8 永远返回 false，所以只有 P1 会变色。现在采集时多存一个 `press_player`（真实字段存 `field.player`，虚拟项存 `token_to_input_type` 返回的玩家号），`field_pressed()` 改用它。
2. **修「选择有赋值却不显示」**：xmen 等 ROM **完全没有 ty=11..14（IPT_SELECT1..4）的 ioport 字段**，遍历 `ioport.ports` 永远找不到「选择」。改为在采集末尾按玩家补一条虚拟项：`ioport:token_to_input_type('P1_SELECT')` 取 type，再 `ioport:type_seq(type, player)` 取通用分配。实测 xmen 得到 `选择:5/6/7/8`，与 MAME 输入配置菜单里的 `Kbd 5/6/7/8` 完全一致。
3. **新增按 ROM 名补 SELECT 的解析分支**：`parse_token()` 增加 `^P(%d+)_SELECT$` → 返回 `(玩家索引, 'SELECT', 'SELECT')`，避免解析不到该 token 时静默丢弃。
4. **新增长键名自动换行**：用户希望「键太多时字体小一点 + 自动换行」。**经核实 MAME 的 `container:draw_text(x, y, text, fg, bg)` 没有字号参数，UI 文字是固定字模，无法调小字号**，因此只实现换行：新增 `split_cell(label, text, maxw)` 返回 1~2 行，压缩顺序为 原样 → 去空格 → 标签独占首行 → 按空格贪心切词；新增 `btn_rows_for()` 让「行数统计」与「实际绘制」用同一套判定，避免高度算错。
5. **换行可按需关闭**：新增设置 `wrap`（默认开），菜单加「长键名自动换行」开关，`serialize()` / `apply_kv()` 均已接入，配置按 ROM 独立保存。
6. **绘制改为「行基线 + 行内偏移」**：选择/开始行与按键行都先算出本行所有格子的最大行数 `need`，再按 `y_base + li - 1` 逐行画，不再多次调用 `row_y()`（那会让同一行被画成多行——这是 v2.0.0 修过的老 bug，本次确认没有回退）。
7. 版本号 2.2.0 → **2.3.0**（`init.lua` 与 `plugin.json` 两处同步）。

### 关键技术决策（本次新增）

|---|---|---|
| 字号能不能调小 | **不能**。MAME UI 文字是固定字模，`draw_text` 无字号参数 | 已通读官方 `ref-render` 文档确认，只能在版式上做文章（缩写 + 换行） |

## 20261108-v4 — v2.4.0

### 变更说明

1. **同时显示键盘与手柄两个绑定**（用户要求「手柄的1也要显示，毕竟已经赋值了」）。此前只取第一个 token，实测 `START = JOYCODE_1_START OR KEYCODE_1`（手柄在前）、`BUTTON1 = KEYCODE_LCONTROL OR … OR JOYCODE_1_BUTTON1`（键盘在前），所以无论取哪一个都会丢另一路。新增 `seq_dual(seq)`：遍历 `input:seq_to_tokens()` 的 token，**键盘取第一个 `KEYCODE_*`、手柄取第一个 `JOYCODE_*`**，两路各取一个后拼成 `键盘 手柄`。
2. **新增手柄缩写 `joy_short()`**：`JOYCODE_1_BUTTON1→J1B1`、`JOYCODE_1_START→J1Sta`、`JOYCODE_1_YAXIS_UP_SWITCH→J1U`、`JOYCODE_1_HAT1DOWN→J1Dn`、`XAXIS_LEFT_SWITCH→J1Lt`、`XAXIS_RIGHT_SWITCH→J1Rt`，其余兜底清洗后截 5 字。
3. **过滤无意义的手柄 token**：实测 P3/P4 的 `START = KEYCODE_3 OR JOYCODE_3_UNKNOWN_SWITCH`，`UNKNOWN_SWITCH` 表示该槽位没有实际绑定。若照常转换会显示成 `J3UN`（本次实测到的 bug），现 `UNKNOWN`/`INVALID` 前缀一律返回 `nil`。
4. **缩写规则按用户要求调整**：
   - `Num` → `N`（`N8`/`NEnt`/`N0`/`NDel`）
   - 方向单字也缩写：`Down→Dn`、`Left→Lt`、`Right→Rt`（`Up` 保持原样，两字已最短）
   - 修饰键左右侧写成 `L-Ctrl`/`R-Ctrl`/`L-Shift`/`R-Shift`/`L-Alt`/`R-Alt`
   - 方位前缀处理必须**放在单字缩写之前**，否则 `Left Ctrl` 的 `Left` 会被当成方向缩成 `Lt`
5. **方向行支持两行排版**：一行四列时每格仅约 82px（约 5.5 个半角宽），而 `Up J1U` 需 6 宽，双路必然被截成 `Up ..`。现格宽不足时改为**上行键盘、下行手柄**，信息不再丢失。
6. **方向行高度四列统一**：`global_dir_need` 取所有列的最大值，只要有一列需要两行，四列都按两行排版。否则 P1 两行、P2 一行会让第 2 列之后的选择/开始行整体上移、与第一列错位（本次实测到该错位后修正）。
7. 版本号 2.3.0 → **2.4.0**（`init.lua` 与 `plugin.json` 两处同步，迭代记录第三处）。

### 关键技术决策（本次新增）

| 问题 | 决定 | 理由 |
|---|---|---|
| 键盘/手柄如何取 | 按 token 类型**各取第一个**，不取「第一个 token」 | 实测 START 手柄在前、BUTTON 键盘在前，取第一个必然丢一路 |

### 变更说明

1. **左右修饰键去掉连字符、压到 5 字**：`ABBR` 表里 `LSHIFT`/`RSHIFT`/`LCTRL`/`RCTRL`/`LALT`/`RALT` 从旧值 `L-Shift`/`R-Shift`/`L-Ctrl`/`R-Ctrl`/`L-Alt`/`R-Alt` 改为 `LShft`/`RShft`/`LCtl`/`RCtl`/`LAlt`/`RAlt`；用户已确认 Win 键一并统一，`L-Win`/`R-Win` → `LWin`/`RWin`。
2. **`shrink_words()` 的 LEFT/RIGHT 分支同步改造**：旧实现返回 `(side=='LEFT' and 'L-' or 'R-') .. table.concat(rest, ' ')`，会产出 `L-Ctrl` 这种带连字符、带空格的形式。现改为不带连字符、直接拼接：`'L' .. table.concat(rest)`。该分支处理的是 MAME 返回的多词名 `Left Ctrl` / `Right Shift`（`ABBR` 表命中的是单 token 形式 `LCTRL` 这种，两条路径都必须改，否则显示不一致）。
3. **新增 `MOD_ABBR` 表**（方位修饰键专用）：`SHIFT→Shft`、`CTRL/CONTROL→Ctl`、`ALT→Alt`、`WIN→Win`、`META/CMD/GUI` 保持原名。**为什么不能复用 `ABBR`**：`ABBR.SHIFT` 要给别处（如单独的 `Shift` 键）保持 `Shift` 这 5 个字符，而方位键必须压成 `Shft` 才能让 `Left Shift` 落成 5 位 `LShft` 而不是 6 位 `LShift`；两者语义不同，共用一张表必然互相污染。
4. **手柄缩写加下划线**：`joy_short()` 收尾 `'J' .. n .. sfx` → `'J' .. n .. '_' .. sfx`。用户确认**全部**加下划线，不止按钮：`J1_B1` / `J1_U` / `J1_Dn` / `J1_Lt` / `J1_Rt` / `J1_Sta` / `J1_Sel`。

> 下划线在本插件里**没有任何语法含义**，纯粹是显示字符，不参与 `match`/`gsub` 的解析——所有 `^JOYCODE_` 等匹配都发生在加下划线之前的原始 token 上。

## 20261109-v11 — v2.8.2（修复 plugin.json 带 UTF-8 BOM 导致插件无法加载）

### 变更说明

1. **用户真机启动即报错，暴露一个致命的编码问题**。MAMEUI64 Plus 弹窗：
   ```
   Unable to parse plugin definition file plugins\mame_kbd\plugin.json.
   Errors returned:
   Invalid value.
   ```
2. **根因：`plugin.json` 带了 UTF-8 BOM（`EF BB BF`）**。MAME 用 rapidjson 系解析器读插件定义，**不接受 BOM**，直接判为非法值。
   核对字节确认引入时点：
   ```
   version/20261108-v1..v8  225 B  前3字节 = 7B 0A 09   无 BOM
   version/20261108-v9      228 B  前3字节 = EF BB BF   有 BOM   ← v2.8.0 起
   version/20261109-v10     228 B  前3字节 = EF BB BF   有 BOM
   ```
   也就是说 **v2.8.0 / v2.8.1 两个版本从部署起就没被 MAME 加载过**，这也解释了为什么始终拿不到任何 `[mame_kbd]` 运行日志——插件根本没起来。
3. **BOM 的来源**：v2.8.0 用 PowerShell `Set-Content -Encoding UTF8` 写回 `plugin.json`。Windows PowerShell 5.1 的 `UTF8` 编码器**默认写 BOM**（`UTF8NoBOM` 才是无 BOM 的那个）。之后的核对只对比了三处 SHA256 是否一致，没有检查首字节，所以一直没发现。
4. **修法**：以二进制方式剥离前 3 字节 BOM，`plugin.json` 从 228 B 回到 225 B，首字节变回 `7B`（`{`），与官方插件（`autofire` 等，`7B 0D 0A 09`）一致。`init.lua` 复查为无 BOM（首字节 `2D 2D 20 6C`，即 `-- l`），不受影响。
5. **新增防回归检查**：`scaffold/_check_lua.py` 增加 `check_encoding_files()`，对插件目录下每个文件检查
   - 是否带 UTF-8 BOM / UTF-16 BOM
   - 是否以 NUL 结尾
   - `*.json` 是否能被 `json.loads` 解析
   并把「编码」作为校验的第一项输出。已用反证脚本确认它能抓到带 BOM 的文件和 JSON 语法坏的文件，正常文件返回空。
6. **版本号 2.8.1 → 2.8.2**（`init.lua:40`、`plugin.json`、本记录三处同步）。版本号递增是为了让「带 BOM 的坏快照」与「能加载的好快照」在版本上可区分。

## 20261109-v20 — v2.9.1（修复镜像蓝/同时金不出现：判据读错了 API）

### 变更说明

用户在真实机台实测 v2.9.0 后反馈（原话）：

> 「被镜像带动的格子应该是蓝色、另一个玩家也按着同一键时应该是金色 这些并没有出现。」

绿色物理高亮正常，蓝与金都不出现。这不是颜色写错，也不是 `copilot2p` 没在工作——**是判定读错了 API**。

#### 根因：`type_pressed` 读的不是最终值

v2.9.0 的假设是「`ioport:type_pressed(ty, pl)` 读字段最终值（含 `set_value` 覆盖），`input:seq_pressed` 读物理量」。**实测证明正好相反。**

为了把这件事钉死，专门写了一个临时探针插件（`scaffold/probe_plugin/`）部署进真实 MAME，对同一个字段 `:P2_P4.P2 Button 1`（`tok=P2_BUTTON1`、`ty=60`、`mask=16`、`defvalue=16`）**每帧持续** `set_value(1)` 模拟 `copilot2p` 的写入，逐帧记录：

```
f10  基线           pp=1 read=65535  band=16  def=16  type_pressed=false 最终值=false → NONE
f12  持续set_value   pp=1 read=65535  band=16  def=16  type_pressed=false 最终值=false → NONE
f13  持续set_value   pp=1 read=65519  band=0   def=16  type_pressed=false 最终值=true  → MIRROR蓝
...
f40  持续set_value   pp=1 read=65519  band=0   def=16  type_pressed=false 最终值=true  → MIRROR蓝
f41  停止写入       pp=1 read=65519  band=0   def=16  type_pressed=false 最终值=true  → MIRROR蓝
f42  停止写入       pp=1 read=65535  band=16  def=16  type_pressed=false 最终值=false → NONE
```

结论（与 v2.9.0 的假设完全相反）：

| API | 实际读的是 | 能否看见 `set_value` 覆盖 |
|---|---|---|
| `ioport:type_pressed(ty, pl)` | **物理设备**状态 | **看不见**（pl=0/1/2/3 恒 false） |
| `port:read()` | **最终值**（含程序化覆盖） | **看得见**（mask 位被清零） |
| `input:seq_pressed(seq)` | 物理设备绑定 | 看不见（与 type_pressed 同类） |

v2.9.0 把 `type_pressed` 当最终值并 `return` 掉了，所以被镜像的格子永远读成「没按」——一直不变色。这是「蓝/金不出现」的唯一根因。

#### 修法一：`field_pressed` 改读 `port:read()`

```lua
local function field_pressed(item)
	local port = item.port
	local m = item.mask
	if port and m and m ~= 0 then
		local v = safe(function() return port:read() end, nil)
		if v ~= nil then
			local cur = band(v, m)
			local dv = item.defvalue
			if dv == nil then return cur ~= 0 end
			return cur ~= band(dv, m)      -- 与 defvalue 同掩码位比较，与端口极性无关
		end
	end
	-- 虚拟项（P1_SELECT / STARTn，没有 port 与 field）只能问官方 API
	...
end
```

**极性判据不能用 `band(v, m) ~= 0`**（v2.9.0 的老写法）。本机未按键时 `port:read()` 返回 `65535`（全 1），按下时对应位**清零**；换成高有效端口就相反。用「与 `defvalue` 的同掩码位比较」才与极性无关。

#### 修法二：`field_physical_pressed` 改以 `type_pressed` 为首选

既然 `type_pressed` 才是物理量，就让它当主判据；`seq_pressed` 降为回退。理由：`seq_pressed` 在取不到 seq 时返回 `false`，若当主判据会把**真实的物理按下误判成镜像**（绿变蓝），比不变色更糟。

#### 修法三：「同时按下」改为逐格时序标记（推翻 v2.9.0 的侧推）

v2.9.0 用「见过镜像 + 另一个玩家此刻也物理按着同一语义键」来侧推「同时」。**这条路有误判**：`copilot2p` 是 P1→P2..P4 **单向**镜像，若 P1 与 P2 同时物理按住 Button1，P1 那格也会被判成金色——但 P1 恰恰是源、从未被写入。

改为逐格时序标记 `mirror_flag`：

```lua
local mirror_flag = {}
local function mirror_key(item)
	return tostring(item.player or 0) .. '|' .. tostring(item.kind or '') .. '|' .. tostring(item.sem or '')
end

local function press_state(item)
	if not item then return PRESS_NONE end
	if not field_pressed(item) then
		mirror_flag[mirror_key(item)] = nil      -- 松开就清标记，下次按下重新判断
		return PRESS_NONE
	end
	local phys = field_physical_pressed(item)
	if phys == nil then return PRESS_PHYS end
	local k = mirror_key(item)
	if not phys then
		mirror_flag[k] = true                     -- 最终值真但物理假 = 只可能是镜像
		return PRESS_MIRROR
	end
	if mirror_flag[k] then return PRESS_BOTH end  -- 先被镜像顶着，自己又物理按下 = 叠加
	return PRESS_PHYS
end
```

这个判据不需要知道镜像源是谁，也不会把「两个人都物理按着同一个键」误判成金色——因为源那一格从来没有「物理假但最终值真」的时刻。

- **镜像蓝**：开 `copilot2p` 镜像后，被镜像带动的格应为**蓝色** `FF40C4FF`。
- **同时金**：某格先被镜像带动（蓝），自己再物理按下 → 转为**金黄** `FFFFD23F`。
- **不误判**：镜像源玩家（P1）自己物理按下的格，即使被控玩家此刻也按着同一键，仍必须是**绿色**。
- 已知保守点：注入 `copilot2p` 之后、本格**第一次被镜像带动之前**，物理按下只显示绿色（没有镜像证据就不敢判「叠加」）。

| 需求 | 为什么这样实现 |
|---|---|
| 为什么是 10 档预设，不是让用户填 #RRGGBB | MAME 插件菜单只有「选一项」和「捕获按键」两种交互（官方 `commonui/init.lua` 实证），既无文本输入也无颜色选择器，做不出填色界面 |

| 为什么不单独开放背景色 | 3 种状态 × 2（字色/底色）会变成 6 个旋钮；而底色本就该跟字色同色系，所以每档打包成一对 |

| 颜色改动不 rebuild_bindings | 绑定文本在采集时算好，颜色只在绘制时取；rebuild 是整表重建，代价大且与颜色无关 |
| 三色允许设成一样 | 用户明确说过「可设成一样，也可任意搭配」；不强加唯一性约束，但默认值必须三者不同（否则升级后用户分不出三种状态） |

## 20261109-v22 — v2.9.3（颜色档位 10 → 30，左右键可长按连发）

### 变更说明

用户反馈「可选颜色颜色太少」。原 `HL_COLORS` 只有 10 档（绿蓝金红紫青橙粉白黄），
做三色搭配时经常找不到合适的中间色，比如想要「浅一点的蓝」或「暗一点的金」都没有。

1. **`HL_COLORS` 10 档 → 30 档**，按色系成组排列：
   - 绿系：green / green_l 浅绿 / green_d 深绿 / lime 黄绿 / mint 薄荷
   - 青系：cyan / aqua 水蓝
   - 蓝系：blue / blue_l 浅蓝 / blue_d 深蓝 / azure 天青 / indigo 靛
   - 紫系：purple / purple_l 浅紫 / purple_d 深紫
   - 粉红系：magenta 洋红 / pink / rose 玫红 / red / red_l 浅红 / red_d 深红 / coral 珊瑚
   - 金橙系：orange / gold / gold_l 浅金 / gold_d 暗金
   - 黄：yellow
   - 中性：white / silver 银 / gray 灰

   排列顺序刻意做成「同一色系里浅→深渐变」，这样按住右键扫过去时看到的是
   一段连续的颜色过渡，而不是每次跳到完全不相干的色，找色效率高得多。

2. **原有 10 个档位的 id 与色值一字未改。** ini 里存的是 id，改 id 等于把用户
   已经配好的颜色重置掉。新档位全部是**插入**到对应色系里，不追加到末尾。

3. **给菜单加了 `lrrepeat`（菜单级 flags）**，左右键按住可连续走档。
   30 档如果只能一次一档地点，从「绿」切到「灰」要按 27 次右键，实际不可用。
   `lrrepeat` 是 populate 的**第三个返回值**（不是菜单项的 flags），
   官方 autofire / inputmacro / offscreenreload 三个插件都在用，本机部署副本已核实：
   - `autofire/autofire_menu.lua:249  return menu, selection, 'lrrepeat'`
   - `inputmacro/inputmacro_menu.lua:615  return items, selection, 'lrrepeat' .. (...)`
   - `offscreenreload/offscreenreload_menu.lua:285  return items, selection, 'lrrepeat'`

   现在 `menu_items()` 末尾返回 `list, nil, 'lrrepeat'`（第二值 nil 表示沿用
   MAME 自己的光标记忆行为）。

### 关键技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 档位规模 | 30 档 | 3 种状态 × 随便挑；再多会让「扫一遍找色」失去意义 |
| 排列方式 | 按色系分组，组内浅→深 | 连续过渡利于目视找色，优于按亮度或字母序 |
| 新档位位置 | 插入对应色系 | 追加到末尾会让「浅蓝」离「蓝」很远，找不到 |
| 老 id / 老色值 | 一字不改 | ini 存 id，改 id = 重置用户配置 |
| 长按连发 | 菜单级 `lrrepeat` | 30 档必须能快速走，官方三插件同法 |

### 校验情况

七套脚本全部通过（失败 0 项）：

- `_check_lua.py`：`HL_COLORS 30 档 id 无重复`、`HL_COLORS 30 档色值两两不同`、
  三个默认值都在表内且互不相同
- `_run_lua.py`（lupa 真跑）：新增两项断言
  - `populate 返回菜单级 flags = 'lrrepeat'（左右键可长按连发）`
  - `「物理按下」切 30 档回到原色（档位规模 20+，切换空间够用）`
- `_verify_colors.py`：持久化闭环不变（写盘 → 新实例重读 → 值不变，非法色名回落）
- `_verify_cols.py` / `_diag8.py` / `_verify_highlight.py`：原有用例不受影响

校验脚本自身适配：`populate` 从返回 1 个值变成 3 个值，lupa 会封成 tuple，
六个脚本里所有直接 `pop()` 后取 `[i][1]` 的地方都会报
`TypeError: 'NoneType' object is not subscriptable`。统一加了一层只取第 1 个值的包装，
需要看 flags 的用例改调 `pop_raw()`。
